# SISTEMA DI DOCUMENTAZIONE SALUTEORA – GUIDA OPERATIVA COMPLETA

## 1. STRUTTURA GERARCHICA E MODULARITÀ
- **Root docs** (`/docs/`): solo indici e collegamenti bidirezionali, MAI documentazione tecnica.
- **Docs modulo** (`Modules/{ModuleName}/docs/`): documentazione tecnica, regole, motivazioni, esempi, anti-pattern, checklist.
- **Docs tema** (`Themes/{Theme}/docs/`): documentazione frontend specifica.
- **Rule files**: `.windsurf/rules/`, `.cursor/rules/` – regole IDE e policy.
- **Documentazione generica**: sempre in Xot, MAI in root.

## 2. NAMING, PERCORSI E COLLEGAMENTI
- **TUTTI i file e cartelle in docs/** devono essere in minuscolo, tranne `README.md`.
- Usare SEMPRE trattini (`-`), MAI underscore (`_`).
- **Mai usare percorsi assoluti** o riferimenti al nome progetto nei link.
- **Sempre percorsi relativi**: calcola i livelli da file sorgente a destinazione.
  - Esempi:
    - Stesso modulo: `./altro-file.md`
    - Modulo a modulo: `../../altro-modulo/docs/file.md`
    - Modulo a root: `../../../../docs/file.md`
    - Root a modulo: `./laravel/Modules/nome-modulo/docs/file.md`
- **Collegamenti bidirezionali obbligatori**: ogni documento deve essere referenziato in `docs/collegamenti-documentazione.md` e avere una sezione "Collegamenti correlati".
- Aggiorna SEMPRE entrambe le direzioni dei collegamenti.
- Usa tag come `#modulo-{nomemodulo}` e `#categoria-{nomecategoria}` per categorizzare.

## 3. POLICY DI AGGIORNAMENTO E MANUTENZIONE
- **Prima di ogni intervento**: analizza tutte le cartelle docs (root e moduli) per comprendere la distribuzione delle responsabilità.
- **Ordine di aggiornamento**:
  1. Documentazione nel modulo specifico
  2. Collegamenti bidirezionali nella root
  3. Regole IDE (.cursor/rules, .windsurf/rules)
  4. Codice effettivo
- **Ogni modifica** (feature, fix, breaking change) va documentata PRIMA nel modulo, POI con collegamenti nella root.
- **Motivazione e "perché"**: ogni regola o variazione deve spiegare la motivazione, non solo il "come".
- **Checklist operativa**: ogni nuova regola, fix o variazione deve essere accompagnata da checklist e motivazione.
- **Esempio pratico e anti-pattern**: ogni regola deve avere almeno un esempio pratico e un anti-pattern.
- **Non duplicare documenti**: sposta i documenti generici dalla root a Xot, lasciando solo i link in root.
- **Documenta breaking changes** e aggiorna sempre la motivazione.
- **Mantieni la retrocompatibilità** quando possibile, documentando le eccezioni.
- **Valida la coerenza** tra docs root, docs modulo, .cursor/rules, .windsurf/rules dopo ogni modifica.
- **Aggiorna sempre la sezione "Collegamenti correlati"** in ogni documento chiave.

## 4. SCRIPT, VALIDAZIONE E AUTOMAZIONE
- **Mai posizionare script o tool in docs/**: usare sempre bashscripts/ o sottocartelle dedicate.
- Gli script vanno in `bashscripts/`, con nomi descrittivi in minuscolo.
- Documenta ogni script in `bashscripts/docs/README.md`.
- Usa script come `fix_docs_case.sh`, `check_docs_naming.sh`, `update_doc_links.sh` per automatizzare naming, percorsi, collegamenti.
- Implementa pre-commit hooks per validazione naming, percorsi, bidirezionalità, struttura.

## 5. FRONTEND E COMPONENTI UI
- Frontoffice: Folio + Volt + Livewire + Widget.
- Template in `Themes/{Theme}/resources/views/pages/`.
- **MAI creare rotte in web.php** – Folio gestisce automaticamente.
- Widget devono estendere `XotBaseWidget` con `HasForms`.
- **MAI estendere direttamente classi Filament**.
- Usare SEMPRE componenti nativi Filament (`<x-filament::icon>`, `<x-filament::button>`, ecc.).
- Per separatori dropdown: `<div class="border-t border-gray-200 dark:border-gray-700 my-1"></div>`.
- La direttiva `@volt` DEVE essere SEMPRE la prima cosa nel file Folio.
- **MAI utilizzare `@volt` all'interno del markup HTML**.
- Usare solo layout corretti: `<x-layouts.app>`, `<x-layouts.guest>`.

## 6. TRADUZIONI E LOCALIZZAZIONE
- File traduzioni in `lang/{locale}/`.
- **MAI usare ->label()** in componenti Filament: usa sempre chiavi di traduzione (`modulo::risorsa.fields.campo.label`).
- Convenzione naming chiavi: `modulo::risorsa.fields.campo.label`.
- Usare `mcamara/laravel-localization` per la localizzazione.
- URL DEVONO includere prefisso lingua: `/{locale}/{sezione}/{risorsa}`.
- **MAI generare URL senza prefisso locale**.

## 7. BACKEND, BUSINESS LOGIC E DIRECTORY
- Usare SEMPRE `spatie/laravel-queueable-action` (MAI Service).
- Componenti Livewire in `app/Http/Livewire` del modulo.
- **Namespace NON deve MAI includere segmento 'app'**.
- Actions nella directory corretta secondo convenzioni.
- Provider in `app/Providers/`.
- Percorso pubblico in `public_html/` (non in `public` di Laravel).
- Vite config temi: `emptyOutDir: false, manifest: 'manifest.json', build: { outDir: './public' }`.
- Documentazione tecnica sezioni in `Themes/{Theme}/docs/sections` e `Modules/Cms/docs/sections` con link bidirezionali.
- JSON configurazione sezioni: ogni blocco deve avere attributo `"view"`, raggruppati per locale, filtrati con `app()->getLocale()`.

## 8. BEST PRACTICES E POLICY
- Usare `Modules\Xot\Contracts\UserContract`.
- Ottenere classe User con `XotData::make()->getUserClass()`.
- Centralizzare logica in traits riutilizzabili.
- Usare enums per stati e valori predefiniti.
- Documentare decisioni architetturali e pattern, sempre con motivazione.
- Aggiornare documentazione CON ogni modifica di codice.
- Ottimizzare per accessibilità, sicurezza e prestazioni.
- Aggiornare prima di implementare correzioni:
  1. Regole in `.windsurf/rules/*.md` per Windsurf
  2. Regole in `.cursor/rules/*.md` per Cursor
  3. Memorie in `.cursor/memories/*.md` per Cursor

## 9. FILAMENT RESOURCES E ARRAY ASSOCIATIVI
- Le funzioni `getTableColumns`, `getTableActions`, `getTableBulkActions` DEVONO restituire array con chiavi stringa.
- Se `getTableActions()` restituisce solo azioni standard (View, Edit, Delete), rimuoverlo completamente.
- Se `getTableBulkActions()` restituisce solo DeleteBulkAction, rimuoverlo completamente.
- Rimuovi override inutili e mantieni solo personalizzazioni reali.
- Ogni funzione che chiama un metodo mancante: documenta prima la necessità, poi implementa nel modulo corretto.
